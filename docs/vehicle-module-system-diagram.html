Engineering Reference — game/src/shared/vehicle

Vehicle Module System

How Last Beacon's modular vehicles are assembled entirely from .bsn data: author-chosen tags, author-chosen socket names, and a connection list that stitches them together — nothing in Rust knows what a specific vehicle looks like.

Worked example verified by game/tests/vehicle_example_two_plate_coupling.rs
01 / 06

Concept

A module is identified purely by its .bsn asset path. Placed in a vehicle, it gets a tag — just its Bevy Name, chosen by whoever authors the vehicle. Each module carries its own sockets, each with an author-chosen name. A connection is a small piece of data naming two tag+socket pairs to join. That's the entire vocabulary — there is no registry, no enum of known modules, no code path that special-cases a particular vehicle layout.

Confirmed by grep: zero references to any concrete module or vehicle name (e.g. "CoreBlock") anywhere in game/src outside test assertions.

"#" is not a comment

In most languages # starts a comment. In this project's .bsn grammar it's literal syntax for a Bevy Name component — #PlateOne means “this entity's Name is PlateOne,” nothing more.

Three similar-looking things exist here — easy to conflate:

  1. A module instance's tag — #PlateOne on the module instance in the vehicle .bsn. Matched by .module_a / .module_b.
  2. A socket's name — the socket_name: "a" field, authored inside the module's own .bsn. Matched by .socket_a / .socket_b.
  3. A socket entity's own #Tag — e.g. #A in coupling_plate.bsn. Just a label; never read by the connection system.

Module Anatomy

Every module authors its shape, physics body, mass, color, and sockets directly — Bevy's/Avian3D's own types, nothing Last-Beacon-specific to keep in sync.

    bevy_transform::components::transform::Transform { translation: glam::Vec3 { x: 0.3, y: 0.0, z: 0.0 } }

    // Normal -X: rotation of PI about Y (local +X -> world -X).
    #B

    bevy_transform::components::transform::Transform { translation: glam::Vec3 { x: -0.3, y: 0.0, z: 0.0 }, rotation: glam::Quat { x: 0.0, y: 1.0, z: 0.0, w: 0.0 } }
    last_beacon::shared::vehicle::LastBeaconVehicleFixedJoint { }
]

#A / #B are Bevy hierarchy tags on the socket entities themselves — unrelated to the module's own vehicle-level tag (#PlateOne, set by whoever places this module in a vehicle).

04 / 06

Socket-Normal Convention

Every socket's local outward normal is local +X. Its Transform.rotation turns that +X to face wherever the socket should actually point. Connecting two sockets only auto-corrects position — the author is responsible for rotating each module so the two sockets' world normals end up opposing each other.

Quat { x: v.x·sin(θ/2), y: v.y·sin(θ/2), z: v.z·sin(θ/2), w: cos(θ/2) }
0° / 180° — no rotation needed, or Quat{x:0,y:1,z:0,w:0} about Y (used by socket "b" above).
90° about Z — core.bsn's Top socket: v=(0,0,1), θ=90°, sin(45°)=cos(45°)≈0.7071068 → Quat{x:0,y:0,z:0.7071068,w:0.7071068}, turning local +X to world +Y.

#Top
…LastBeaconVehicleModuleSocket { socket_name: "top" }
…Transform {
  translation: { x: 0.0, y: 0.5, z: 0.0 },
  rotation: {
    x: 0.0, y: 0.0,
    z: 0.7071068, w: 0.7071068
  }
}

Connections & Resolution

A vehicle .bsn places module instances (each tagged with a Name) and lists connections naming two tag+socket pairs. wire_last_beacon_vehicle_connections resolves each one purely from these strings.

two_plate_coupling.bsn.bsn
#PlateOneToPlateTwo
last_beacon::shared::vehicle::LastBeaconVehicleConnection {
  module_a: "PlateOne", socket_a: "a",
  module_b: "PlateTwo", socket_b: "b"
}
mod.rs — the struct behind itrust
pub struct LastBeaconVehicleConnection {
    module_a: String,
    socket_a: String,
    module_b: String,
    socket_b: String,
}

Resolution pipeline, once per frame, in Update:

queue_*
start .bsn load
apply_pending_*
materialize module
materialize_*
mesh · collider
wire_connections
fuse or hinge

Diagnosing A Bad Connection

A typo'd tag or socket name doesn't fail silently. The connection is marked LastBeaconVehicleConnectionFailed (never Resolved), the warning lists every valid candidate, and — with dev-tools enabled — a red marker is drawn in-scene.

example: connection.socket_b = "z" (doesn't exist)
connection.rs — the failure markerrust
pub struct LastBeaconVehicleConnectionFailed {
    pub reason: String,
    pub marker_position: Option<Vec3>,
}

// warn!("… socket `z` not found on module `PlateTwo` (available sockets: a, b); skipping.")
